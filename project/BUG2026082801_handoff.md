## 1. 증상

CodeMirror 6 기반 블록 에디터에서 `ArrowUp`/`ArrowDown`으로 커서를 수직 이동시키면
**줄을 하나씩 건너뛴다.** 사용자 원 보고는 "블록쿼트(`>`) 구간에서, ArrowUp이 더
빈번, 간헐적"이었으나, 이번 조사에서 **블록쿼트와 전혀 무관한 순수 평문에서도
동일하게 재현됨**을 확인했다. 즉 제목과 달리 **블록쿼트 한정 버그가 아니다.**

## 2. 재현 절차 (T3 실기, 100% 가까운 재현율)

WKWebView에 `tauri-plugin-mcp-bridge`(디버그 전용, 검증 후 즉시 제거함)로 연결해
`webview_keyboard`(action: "press")로 **진짜 네이티브 키 이벤트**를 주입하고,
`view.state.selection.main.head` → `doc.lineAt(head).number`로 라인 번호를 측정했다.

### 재현 문서 A — 순수 평문 (결정적 반증용, 블록쿼트/데코레이터 매치 0건)

```markdown
# Plain Only Test

Plain line A QA-A
Plain line B QA-B
Plain line C QA-C
Plain line D QA-D
Plain line E QA-E
Plain line F QA-F
Plain line G QA-G
```

측정 순서 (전부 실키 `ArrowDown`, 사이에 다른 조작 없음):

| 단계 | 시작 줄 | 키 | 도착 줄 | 기대 delta | 실제 delta |
|---|---|---|---|---|---|
| 1 | line 1 (`# Plain Only Test`) | ArrowDown | line 2 (빈 줄) | 1 | **1 (정상)** |
| 2 | line 2 (빈 줄) | ArrowDown | line 4 (`Plain line B`) | 1 | **2 (line 3 `Plain line A` 스킵)** |
| 3 | line 4 | ArrowDown | line 6 (`Plain line D`) | 1 | **2 (line 5 스킵)** |

별도 시도: 커서를 `view.dispatch({selection:{anchor: <"Plain line A" 시작 위치>}})`로
프로그래매틱 배치한 뒤 **처음** 누르는 real ArrowDown 한 번만으로도 곧바로
line3→line5 스킵이 재현됨 — "몇 번째 키 입력인지"가 결정 요인은 아닌 것으로 보인다
(다만 재현 조건을 체계적으로 격자 탐색하지는 못했다 — §6 참조).

### 재현 문서 B — 블록쿼트 포함 (원 보고 재현용)

```markdown
# Blockquote Cursor Test

Plain line before quote QA-BEFORE

> Quote line 1 QA-Q1
> Quote line 2 QA-Q2
> Quote line 3 QA-Q3
> Quote line 4 QA-Q4
> Quote line 5 QA-Q5

Plain line after quote QA-AFTER

> Solo quote line QA-SOLO

Plain line 2 QA-AFTER2

>
> Quote after empty marker QA-EMPTYMARK

Plain line 3 QA-END
```

`"Quote line 1 QA-Q1"` 시작 위치에 커서를 두고 실키 ArrowDown 연타:
line 5 → 7 → 9 → 11 → 13 (매번 delta=2, 블록쿼트 구간을 벗어난 뒤로도 계속됨).
이 패턴은 **H1/H2/H3 세 가지 fix를 각각 단독/누적 적용해도 전혀 변하지 않았다**
(아래 §3).

## 3. 기각된 가설 (전부 코드 변경 후 실기 재검증, 최종적으로 전부 롤백함)

원 티켓(`ticket/debug/20260828_1920_blockquote_vertical_cursor_skip.yml`)이 제시한
가설과 그 근거는 다음과 같았으나 전부 반증됨:

- **H2** — `BlockquoteDecorator.ts`의 `HIDE_DECO = Decoration.replace({})`에
  `bidiIsolate: false`가 없음(다른 데코레이터인 Heading/List/Checkbox는 전부 명시).
  → **적용해도 스킵 그대로 재현.**
- **H1** — 위젯 없는 `replace({})`. Heading/List/Checkbox는 전부 `WidgetType` 위젯을
  가진 replace를 쓰는데 Blockquote만 위젯이 없음.
  → H2와 함께 적용해도 **변화 없음.**
- **H3** (원 티켓 최우선 가설) — "커서가 있는 줄에만 `>` 마커를 노출"하는 정책 때문에
  수직 이동마다 출발 줄(-2자)/도착 줄(+2자)의 가시 길이가 바뀌어 CodeMirror의
  goal column이 오염된다는 가설. 마커 노출 정책을 "커서 줄" → "커서가 속한 블록쿼트
  구간 전체"로 재설계해 **DOM에서 구간 전체 마커가 실제로 노출되는 것까지 재확인**했음에도
  (즉 이동 중 가시 콘텐츠 길이가 전혀 안 바뀌는데도) **스킵이 동일하게 재현됨.**
  → H3의 핵심 메커니즘("마커 토글이 goal column을 무효화한다") 자체가 틀렸다는
  결정적 반증.
- **결정타**: 블록쿼트가 전혀 없는 순수 평문(재현 문서 A)에서도 동일 패턴 재현.
  → 원인이 `BlockquoteDecorator.ts` 안에 있을 수 없다.

세 가설의 코드 변경은 전부 롤백했다. **현재 `BlockquoteDecorator.ts`는 이 조사
착수 이전(HEAD) 상태 그대로**이며, 아래 §4의 코드가 최신이다.

## 4. 현재 관련 코드 (조사 시작점)

### 4.1 `project/src/shared/lib/editor/decorators/impl/BlockquoteDecorator.ts` (전체, 원본 그대로 — 원인 아님이 확인된 상태)

```ts
import { Decoration, DecorationSet } from '@codemirror/view';
import { EditorState, RangeSetBuilder } from '@codemirror/state';
import { SyntaxDecorator } from '../types';

const BLOCKQUOTE_RE = /^>\s?(.*)$/;
const HIDE_DECO = Decoration.replace({});

export class BlockquoteDecorator implements SyntaxDecorator {
  readonly name = 'blockquote';

  createDecorations(state: EditorState, from: number, to: number): DecorationSet {
    const { doc } = state;
    const cursorHead = state.selection.main.head;

    interface DR { from: number; to: number; deco: Decoration; }
    const ranges: DR[] = [];

    let pos = from;
    while (pos <= to) {
      const line = doc.lineAt(pos);
      const lineText = doc.sliceString(line.from, line.to);
      const match = BLOCKQUOTE_RE.exec(lineText);

      if (match) {
        let isPrevBq = false;
        if (line.number > 1) {
            isPrevBq = BLOCKQUOTE_RE.test(doc.line(line.number - 1).text);
        }

        let isNextBq = false;
        if (line.number < doc.lines) {
            isNextBq = BLOCKQUOTE_RE.test(doc.line(line.number + 1).text);
        }

        let blockClass = 'cm-blockquote-single';
        if (isPrevBq && isNextBq) blockClass = 'cm-blockquote-middle';
        else if (isPrevBq) blockClass = 'cm-blockquote-bottom';
        else if (isNextBq) blockClass = 'cm-blockquote-top';

        const markerEnd = line.from + (lineText.startsWith('> ') ? 2 : 1);

        ranges.push({
          from: line.from,
          to: line.from,
          deco: Decoration.line({ class: `cm-blockquote-line ${blockClass}` })
        });

        // Hide marker if cursor is NOT on this line
        if (line.number !== doc.lineAt(cursorHead).number) {
            if (markerEnd <= line.to) {
                ranges.push({ from: line.from, to: markerEnd, deco: HIDE_DECO });
            }
        }
      }
      pos = line.to + 1;
    }

    ranges.sort((a, b) => a.from - b.from);

    const builder = new RangeSetBuilder<Decoration>();
    for (const r of ranges) {
      builder.add(r.from, r.to, r.deco);
    }

    return builder.finish();
  }
}
```

### 4.3 `project/src/shared/lib/editor/decorators/orchestrator.ts` — **가장 유력한 신규 단서**

`markdownDecorationPlugin`을 만드는 팩토리(`createDecorationPlugin`)의 핵심부:

```ts
const decorationStateField = StateField.define<DecorationSet>({
  create(state) {
    return buildAll(state, decorators);
  },
  update(value, tr) {
    if (tr.state.field(imeStateField, false)) {
      if (tr.docChanged) return value.map(tr.changes);
      return value;
    }

    // ★ tr.selection 이 true 이면 (= 커서가 움직이는 모든 트랜잭션 포함)
    //   11개 데코레이터(Heading/List/Checkbox/Blockquote/CodeBlock/Latex/
    //   Hyperlink/Image/Strikethrough/BoldItalic/HorizontalRule) 전체를
    //   블록 전체 range(0~doc.length)에 대해 매번 처음부터 다시 계산한다.
    if (tr.docChanged || tr.selection || tr.effects.some(e => e.is(setImeEffect))) {
      return buildAll(tr.state, decorators);
    }

    return value;
  },
  provide: (f) => EditorView.decorations.from(f)
});
```

`buildAll`은 전체 블록(`from=0, to=doc.length`)에 대해 등록된 모든 데코레이터의
`createDecorations`를 매번 새로 호출하고 `RangeSet.join`으로 합친다 — **가벼운
작업이 아니다.** 그리고 이게 **ArrowUp/ArrowDown이 발생시키는 바로 그 트랜잭션
안에서, `defaultKeymap`의 커서 이동 커맨드와 같은 dispatch 사이클에** 일어난다.

**이것이 다음으로 파야 할 가장 유력한 지점이라고 판단하는 이유**:
- 순수 평문에서도 재현된다는 사실과 모순되지 않는다 — Heading 등 다른 데코레이터도
  매 선택 변경마다 재계산되므로, 특정 데코레이터의 내용과 무관하게 "재계산 자체가
  일어난다"는 사실만으로 문제가 생길 수 있다.
- CodeMirror 6의 `cursorLineDown`/`Up`은 일반적으로 실제 DOM 레이아웃을 측정해
  다음 줄 위치를 찾는다(단순 산술이 아님). 만약 이 측정이 **decoration이 갱신되기
  전** 시점의 레이아웃을 참조하거나, 반대로 **아직 완전히 반영되지 않은 갱신
  직후**의 레이아웃을 참조한다면, 매 이동마다 "한 사이클 뒤처진" 좌표를 기준으로
  움직여 결과적으로 한 줄씩 밀리는 현상이 나타날 수 있다.
- `tr.selection`에 반응해 **매번** 전체 재계산이 일어나는 구조 자체가 애초에
  CodeMirror 6의 권장 패턴(뷰포트 단위 증분 갱신)과 다르다 — 이 프로젝트는
  "블록 = 별도 EditorView, 블록 내용이 작으니 전체를 매번 다시 파싱해도 된다"는
  전제(`orchestrator.ts` 상단 주석 참고)로 설계되어 있는데, 그 전제가 vertical
  motion과 상호작용해 이 버그를 만들 가능성이 있다.

   `@codemirror/commands@6.10.4`, `@codemirror/view@6.43.6`, `@codemirror/state@6.7.1`.
2. **`orchestrator.ts`의 `tr.selection` 트리거 제거 실험** — 데코레이션 재계산을
   `tr.docChanged`에만 반응하도록 임시로 좁혀서(커서 이동 시 재계산 안 함) 스킵이
   사라지는지 확인. 사라진다면 §4.3의 가설이 맞다는 강력한 증거이며, 그 경우
   "커서 위치에 따라 마커를 숨기는" 기능들(Heading/List/Checkbox/Blockquote가
   전부 `cursorHead`를 씀)을 어떻게 유지하면서 재계산 비용/타이밍을 줄일지가
   진짜 수정 범위가 된다.
3. **`EditorView.updateListener`의 `update.focusChanged`/`update.selectionSet`
   순서와, `view.moveVertically` 또는 CM6가 내부적으로 쓰는 유사 API가 언제
   `measureRequested`/reflow를 트리거하는지** — CodeMirror 6 소스의 `ViewUpdate`,
   `DocView`, `heightmap` 관련 코드.
4. **실제 물리 키보드로 사람이 직접 재현** — 이번 T3 재현은 `webview_keyboard`
   자동화 도구가 만든 것이며, 사람이 실제로 화살표 키를 눌렀을 때도 100%에
   가깝게 재현되는지는 확인하지 못했다. 원 사용자 보고는 "간헐적"이었다는 점과
   이번 재현의 "거의 항상"이라는 결과 사이의 간극을 반드시 좁힐 것.
5. 재현이 더 필요하면 위 §2의 두 문서를 그대로 복원해 쓸 것(이번 세션에서
   만든 `project/qa_fixtures/`는 정리되어 삭제됨 — 필요시 위 마크다운을
   그대로 파일로 재생성하면 됨).

## 7. 세션 중 확인된 부수 사실 (참고용, 버그 자체와 직접 관련은 없음)

- 이 앱은 헤딩(H1~H3)마다 별도 `EditorView`를 만든다. 순수 평문 문서(`# Plain
  Only Test` + 평문 줄들)는 헤딩이 하나뿐이라 **문서 전체가 하나의 EditorView**다.
- `document.hasFocus()`가 `false`인 상태(OS 창이 key window가 아닌 상태)에서는
  `webview_keyboard`/합성 이벤트가 신뢰할 수 없게 동작한다(엉뚱한 곳에 입력되거나
  무시됨). 반드시 실제 OS 포커스가 잡힌 상태에서 검증할 것.
- 합성 `KeyboardEvent`를 `dispatchEvent`로 직접 쏘는 방식은 이중 발화처럼 보이는
  아티팩트가 있어 신뢰할 수 없었다 — **반드시 `webview_keyboard`의 실제 키
  주입만 사용할 것.**
