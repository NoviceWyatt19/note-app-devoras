## 3. 원인 가설 (근거와 함께, 신뢰도 순)

### H1 — 포커스 스왑 자체가 두 블록의 높이를 동시에 바꾼다 🔴 **주원인 후보**

포커스된 블록은 **원본 마크다운**을, 나머지는 **렌더된 HTML**을 보여준다([`BlockEditor.tsx:308-326`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L308)). 두 표현의 높이는 구조적으로 다르다.

| 블록 내용 | 렌더 HTML (`rv-content`) | 원본 마크다운 (CodeMirror) | Δ |
|---|---|---|---|
| 이미지 1장 | `<img>` 실측 높이 (수백 px) | 위젯 최대 300px, **로드 전 0px** | 수백 px |
| 코드펜스 | 헤더 바 35px + `pre` + `my-4 mx-4` 여백 | 위젯 헤더 + 라인 | 수십 px |
| H1 블록 | `.rv-content h1` 35px ([`index.css:71`](src/app/styles/index.css#L71)) | `.cm-h1` 미반영 14px (**Stage D 스코프 밖 — §6**) | ~25px |
| 표 / 인용 / 리스트 | 전용 스타일 | 원본 파이프·`>`·`-` 텍스트 | 가변 |

**A 가 B 보다 위에 있으면 ΔA 만큼 B 가 통째로 밀린다.** `scrollTop` 은 그대로인데 콘텐츠가 움직이므로 사용자에게는 "스크롤이 튀었다"로 보인다.

> ⚠️ **WKWebView 에는 scroll anchoring 이 없다.** Chromium 은 뷰포트 위쪽 콘텐츠의 높이 변화를 `scrollTop` 으로 자동 보정하지만(`overflow-anchor`), WebKit 은 이 기능을 구현하지 않는다. 즉 **Tauri(macOS/WKWebView)에서만 재현되고 브라우저 `pnpm dev` 로는 재현되지 않을 수 있다.** §4 D-0 의 환경 고정이 필수인 이유다.

### H2 — 이미지 위젯의 비동기 로드가 스왑 이후에 높이를 또 바꾼다 🔴 **높음**

[`ImageDecorator.ts:34-68`](src/shared/lib/editor/decorators/impl/ImageDecorator.ts#L34) 은 `<img>` 를 **1×1 투명 GIF** 로 먼저 붙이고, 실제 `src` 를 나중에 넣은 뒤 `img.onload → view.requestMeasure()` 로 재측정한다. 즉 포커스를 받은 블록의 이미지는 **0px → 최대 300px** 로 늦게 자란다.

반대 방향도 마찬가지다. 포커스를 잃은 블록은 새 `<div class="rv-content">` 로 **마운트**되므로 `<img>` 가 새로 생성되고, [`index.css:151`](src/app/styles/index.css#L151) 의 `.rv-content img { max-width: 100% }` 에는 **높이·`aspect-ratio` 예약이 없어** 로드 전 0px 다.

**결과: 클릭 직후가 아니라 수 프레임 뒤에 레이아웃이 크게 재배치된다.** 신고의 "엉뚱한 구간이 표시된다"와 정확히 일치한다.

### H3 — `focus()` + `dispatch({selection})` 가 상위 스크롤러를 이동시킨다 🟠 **중간~높음**

[`BlockEditor.tsx:245-259`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L245):

```ts
if (!view.hasFocus) view.focus();            // ① 이 시점 selection anchor = 0 (문서 처음)
const currentAnchor = view.state.selection.main.anchor;
if (currentAnchor !== targetOffset) {
  view.dispatch({ selection: { anchor: targetOffset, head: targetOffset } });  // ② 보호 없음
}
```

- **①** `view.focus()` 는 내부적으로 `focusPreventScroll()` 을 쓴다(`@codemirror/view@6.43.6`, `dist/index.js:691`). 그런데 같은 파일 `:686-688` 에:
  ```js
  // Safari 26 breaks preventScroll support
  if (browser.safari && browser.safari_version >= 26) preventScrollSupported = false;
  ```
  **Tauri macOS 는 WKWebView = Safari 엔진이다.** Safari 26+ 에서는 `preventScroll` 이 비활성화되고, 조상들의 `scrollTop` 을 미리 저장했다가 `focus()` 직후 **동기적으로 되돌리는 폴백**이 동작한다. WebKit 이 포커스 스크롤을 다음 프레임에 지연 적용하면 이 복원은 무력하다.
- **①** 은 또 `selection anchor = 0`(블록 맨 앞) 상태에서 포커스한다. **문서 위쪽으로 한 번**.
- **②** 는 `preventScroll` 보호가 전혀 없는 별도 dispatch 다. `targetOffset = block.content.length`(§H5)이므로 **블록 맨 끝, 즉 아래쪽으로 한 번 더**.

**"위 또는 아래로" 라는 신고의 양방향성이 ①→② 2단 이동과 부합한다.**

### H4 — CM 이 DOM selection 을 되읽어 `scrollIntoView: true` 로 dispatch 한다 🟠 **중간**

`@codemirror/view` `dist/index.js:4296-4304`:

```js
let scrollIntoView = false, userEvent = "select";
if (view.inputState.lastSelectionTime > Date.now() - 50) {
  if (view.inputState.lastSelectionOrigin == "select") scrollIntoView = true;
  ...
}
view.dispatch({ selection: newSel, scrollIntoView, userEvent });
```

그리고 `scrollRectIntoView`(`dist/index.js:540-556`)는 **`scrollDOM` 에서 시작해 조상을 타고 올라가며 스크롤 가능한 요소를 전부 이동시킨다.** `.cm-scroller` 에 `overflow: hidden` 이 걸려 있어도([`BlockEditor.tsx:78-83`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L78)) `scrollHeight <= clientHeight` 조건에 걸려 그냥 통과되고, **결국 [`WorkspacePage.tsx:349`](src/pages/WorkspacePage/WorkspacePage.tsx#L349) 의 `overflow-y-auto` 가 움직인다.**

즉 `.cm-scroller { overflow: hidden }` 은 CM 의 스크롤을 막는 것이 아니라 **패널 컨테이너로 전가**한다.

### H5 — 클릭 오프셋이 "클릭 지점"이 아니라 "블록 끝"이다 🟠 **중간 · 신고와 불일치**

[`BlockEditor.tsx:306`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L306):

```tsx
onClick={() => !isFocused && focusBlock(block.id, block.content.length)}
```

클릭 좌표를 전혀 쓰지 않고 **무조건 블록 콘텐츠 끝**으로 캐럿을 보낸다. 100줄짜리 블록의 첫 줄을 클릭해도 캐럿은 100번째 줄에 놓인다.

> **⚠️ 신고("캐럿은 정상 배치된다")와 코드가 어긋난다.** 가능한 해석은 둘뿐이다.
> - (a) 신고가 부정확하다 — 짧은 블록에서는 끝 = 클릭 지점과 거의 같다.
> - (b) H4 의 DOM selection 되읽기가 스토어 값을 덮어써 클릭 지점에 캐럿을 놓는다. **이 경우 캐럿이 맞는 이유와 스크롤이 튀는 이유가 동일한 코드 경로다.**
>
> **§4 D-1 의 M7 에서 반드시 판별할 것.** (b) 라면 H4 가 주원인으로 승격되고 수정 우선순위가 바뀐다.

### H6 — passive effect 타이밍으로 "빈 프레임"이 생긴다 🟡 **낮음~중간 · 저비용 수정**

CM 생성([`:132`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L132))과 포커스([`:245`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L245))가 모두 **`useEffect`(passive)** 다. 같은 파일의 다른 곳은 이미 `useLayoutEffect` 를 쓰고 있다([`:356`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L356), [`:384`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L384), [`:399`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L399)) — **일관성이 없다.**

커밋 시점에 클릭된 블록은 `<div ref={containerRef} class="w-full" />` **빈 컨테이너(높이 0)** 다. passive effect 가 페인트 뒤에 밀리면 사용자는 블록이 **붕괴했다가 되살아나는** 프레임을 본다.

### H7 — 포커스/비포커스 래퍼의 패딩이 비대칭이다 🟡 **낮음 · 결정론적**

[`BlockEditor.tsx:262-270`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L262) 의 `CodeMirrorBlock` 루트에는 `py-1`(상하 4px씩)이 있는데, 비포커스 분기 [`:320-325`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L320) 의 `rv-content` 에는 없다. 포커스 전환 1회마다 **두 블록에서 각각 ±8px**, 합계 최대 16px 이 확정적으로 움직인다.

### H8 — `focusOffset` 이 전 블록에 prop 으로 흘러 전체 트리를 리렌더한다 🟡 **낮음 (성능)**

`focusOffset` 은 모든 `BlockNode` 에 prop 으로 전달되므로([`:334`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L334)) 포커스가 바뀔 때마다 `React.memo` 가 전부 무효화되고 `renderBlockToHtml` 이 블록 수만큼 재실행된다([`:323`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L323)).

React 는 `dangerouslySetInnerHTML.__html` 을 **문자열 값으로 비교**하므로 DOM 은 갱신되지 않는다 — **레이아웃 시프트의 직접 원인은 아니다.** 다만 클릭 → 커밋 사이의 지연을 늘려 H6 의 붕괴 프레임을 길게 만든다. 이번 배치에서는 **수정하지 않고 계측만** 한다.

### 조기 배제 — 다시 조사하지 말 것

| 배제 대상 | 근거 |
|---|---|
| `scrollIntoView()` / `scrollTop` 직접 호출 | `src/` 전수 grep 결과 **호출 지점 0건**. 스크롤은 전부 CM 내부 또는 브라우저 기본 동작이다 |
| `setBlocksFromContent` 활성 ID 폴백 | 클릭 경로에서 호출되지 않음 (§1.4) |
| `dangerouslySetInnerHTML` 재삽입 | React 가 문자열 동등 비교로 스킵 (H8) |

## 4. Stage D 실행 계획

> **원칙**: **먼저 무조건적인 방어선(D-2)을 세우고, 그 다음에 개별 원인을 제거(D-3~D-5)한다.** 원인이 여러 개이므로 개별 제거만으로는 잔여 시프트가 남는다.

### D-0. 환경 고정 (선행 · 생략 금지)

| 항목 | 지시 |
|---|---|
| 실행 환경 | **`pnpm tauri:dev` 로만 재현·검증한다.** `pnpm dev`(Chromium 계열)는 scroll anchoring 때문에 증상이 **가려진다**(H1 주석) |
| 문서 | 화면 3배 이상 높이 + H2 블록 6개 이상 + **이미지 1장 이상** + 코드펜스 1개 이상 |

### D-1. 계측 — 어느 가설이 몇 px 를 먹는지 수치화

### D-2. 스크롤 앵커 보존 — 무조건적 방어선 🔴 **최우선**

원인이 H1·H2·H3 중 무엇이든, **클릭한 요소의 뷰포트 내 Y 좌표를 스왑 전후로 동일하게 유지**하면 사용자에게는 점프가 사라진다 (FLIP 기법).

수정 지점: [`BlockEditor.tsx:302-327`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L302) (`BlockNode`)

1. `onClick` 에서 `focusBlock` 호출 **직전**에, 클릭된 엘리먼트의 `getBoundingClientRect().top` 과 스크롤 컨테이너 참조를 모듈 스코프 변수에 기록한다.
2. `useLayoutEffect`(커밋 직후 · 페인트 **전**)에서 같은 엘리먼트의 `rect.top` 을 다시 재고, 차이만큼 `scrollContainer.scrollTop += (newTop - oldTop)` 로 보정한다.
3. 스크롤 컨테이너는 **DOM 을 타고 올라가 `overflow-y` 가 `auto|scroll` 인 최초의 조상**을 찾는다(`getScrollParent`). `WorkspacePage` 에서 ref 를 내려보내지 않는 이유: 분할 패널마다 컨테이너가 다르고([`WorkspacePage.tsx:220-228`](src/pages/WorkspacePage/WorkspacePage.tsx#L220)), prop drilling 은 **REF-20260826-01(탭 스코프 Context)** 과 충돌한다. `closest` 탐색은 그 리팩터링과 독립적이다.
4. **비동기 성장(H2)까지 덮는다**: 보정 대상 블록 안의 `<img>` 중 `complete === false` 인 것에 `load` 리스너를 붙여, 로드마다 같은 보정을 1회 더 수행한다. 리스너는 `{ once: true }` 로 붙이고 블록 언마운트 시 정리한다.

**금지 사항**
- `scrollIntoView()` 를 새로 도입하지 말 것. 그것은 "다른 곳으로 스크롤"이지 "제자리 유지"가 아니다.
- `scroll-behavior: smooth` 를 쓰지 말 것. 보정이 애니메이션되면 점프가 더 눈에 띈다.
- 보정을 `useEffect`(passive)에 두지 말 것. 페인트 뒤에 실행되면 사용자가 점프를 **본 뒤에** 되돌아온다 — 증상이 "깜빡임"으로 바뀔 뿐이다.

### D-3. 포커스·셀렉션 전이의 스크롤 유발 제거

수정 지점: [`BlockEditor.tsx:245-259`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L245)

1. **`focus()` 전에 셀렉션을 먼저 확정한다.** 현재는 `anchor = 0` 으로 포커스한 뒤 끝으로 옮겨 **2단 이동**이 생긴다(H3). `dispatch({selection})` → `view.focus()` 순서로 뒤집어 이동을 1회로 줄인다.
2. **초기 셀렉션을 마운트 시점에 넣는다.** [`:176-221`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L176) 의 `EditorState.create({ doc })` 에 `selection: { anchor: clampedFocusOffset }` 를 함께 넘기면, 마운트 직후 포커스 effect 가 셀렉션을 옮길 필요 자체가 없어진다. **가장 깨끗한 해법이며 D-3 의 본체다.**
3. **`scrollIntoView` 를 명시적으로 억제한다.** 남는 `dispatch` 에는 `scrollIntoView: false` 를 명시하고, `userEvent` 를 `'select'` 로 두지 않는다 — H4 의 50ms 창(`lastSelectionOrigin == "select"`)에 걸리지 않게 한다.
4. `.cm-scroller { overflow: hidden }`([`:78-83`](src/widgets/BlockEditor/ui/BlockEditor.tsx#L78))은 **유지한다.** 이것은 스크롤을 막는 게 아니라 패널로 전가할 뿐이지만(H4), 제거하면 블록마다 내부 스크롤바가 생겨 UX 가 더 나빠진다. 전가된 스크롤은 D-2 가 흡수한다.

### D-4. DOM selection 되읽기 차단 (M7 = (b) 인 경우 **D-2 다음으로 승격**)

클릭이 남긴 DOM selection 이 정적 HTML div 에 있는데 그 div 가 제거되고 CodeMirror 가 그 자리에 들어서므로, CM `DOMObserver` 가 selection 을 되읽어 `scrollIntoView: true` 로 dispatch 할 수 있다(H4).

1. `BlockNode` 의 `onClick` 에서 `focusBlock` 호출 직전에 `window.getSelection()?.removeAllRanges()` 로 **잔여 selection 을 명시적으로 비운다.**
2. **클릭 좌표를 실제 오프셋으로 변환하는 것을 D-2/D-3 이후로 미룬다.** `content.length` 는 명백히 틀렸지만(H5), 캐럿 위치 수정은 **캐럿 회귀 기제와 맞물리므로 §6 스코프 밖**이다. 이번 배치에서는 **동작을 바꾸지 말고**, M7 결과와 함께 **별도 티켓으로 분리 발행**한다.

> **이유**: 스크롤 점프를 잡는 배치에서 캐럿 배치까지 함께 바꾸면 **회귀 원인을 분리할 수 없다.** 한 배치 = 한 관심사.
