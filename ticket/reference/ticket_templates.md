

## 1. Session Ticket (세션 티켓)

> **목적:** AI 또는 협업자와의 1회성 대화/코드 세션을 마친 후, 핵심 요약과 구현 디테일을 분리하여 기록하고 컨텍스트를 유지합니다.

```markdown
# [Session] {세션 주제 한 줄 요약}

## 📌 1. 핵심 요약 (TL;DR)
* **주요 성과:** 이번 세션에서 달성한 핵심 결과물이나 결론
* **현재 상태:** 작업이 멈춘 시점의 최종 상태

## 🔍 2. 세부 결정 및 구현 디테일
### 팩트 및 의사결정
* [Decision] {선택한 아키텍처, 라이브러리, 혹은 접근 방식}
* [Reason] {해당 결정을 내린 이유나 배경}

### 코드/기술적 변경점
* **변경 모듈/파일:** `{예: MemberService.java, auth_store.dart}`
* **핵심 로직 변경:** `{기존 구조에서 변경된 핵심 로직의 개념적 설명}`

## 🛠️ 3. 컨텍스트 및 참고 사항
* **미해결 질문:** 세션 중 논의되었으나 결론이 나지 않은 부분
* **참고 레퍼런스:** 관련 링크, 사용한 프롬프트, 혹은 참고한 공식 문서

```

## 2. Implement Ticket (구현 티켓)

> **목적:** 명확한 스펙 정의를 통해 기능 구현의 입출력과 내부 동작을 규정하고, 헤매지 않고 바로 코딩에 들어갈 수 있도록 가이드합니다.

```markdown
# [Implement] {기능명 또는 컴포넌트명}

## 🎯 1. 기능 개요 및 목적
* **설명:** 이 기능이 왜 필요하며, 유저나 시스템에 어떤 가치를 제공하는지 기술합니다.

## 📋 2. 요구 사항 (Requirements)
* [ ] {반드시 만족해야 하는 기능적/비기능적 조건 1}
* [ ] {반드시 만족해야 하는 기능적/비기능적 조건 2}

## 🔄 3. 데이터 흐름 (Input & Output)
| 구분 | 타입 / 포맷 | 설명 |
| :--- | :--- | :--- |
| **Input (입력)** | `DTO` / `JSON` / `Parameters` | 데이터 진입점 및 필수 값 |
| **Output (출력)** | `Response` / `UI State` | 성공/실패 시 반환되거나 렌더링될 데이터 |

## ⚙️ 4. 내부 동작 및 비즈니스 로직 (Internal Logic)
* **단계별 동작:**
  1. `{인증 및 유효성 검증 단계}`
  2. `{도메인 객체로의 위임 또는 비즈니스 로직 처리}`
  3. `{DB 저장 또는 외부 API 호출 (예: QueryDSL Projection 활용 등)}`
* **예외 처리:** `{예: 데이터 미존재 시 404 Custom Exception 발생}`

## 🚀 5. 다음 단계 (Next Steps)
* [ ] `{도메인 엔티티 및 비즈니스 로직 구현}`
* [ ] `{단위 테스트(Unit Test) 작성}`
* [ ] `{API 엔드포인트 연동 및 통합 테스트}`

```

## 3. Debug Ticket (디버그 티켓)

> **목적:** 에러나 버그가 발생했을 때 현상을 박제하고, 원인 추론과 해결 과정을 기록하여 추후 동일한 이슈를 방지합니다.

```markdown
# [Debug] {에러 메시지 요약 또는 버그 현상}

## 🚨 1. 발생 현상 (Symptom)
* **상황:** 어떤 액션을 취했을 때 문제가 발생하는지 기술
* **재현 경로:** `{예: 로그인 버튼 클릭 -> 이메일 인증 캐싱 확인 -> 에러 발생}`
* **에러 로그 / 스크린샷:**

```

{여기에 Stack Trace 또는 에러 로그 붙여넣기}

```

## 🔍 2. 원인 분석 및 유추 (Root Cause Analysis)
* **가설 1:** `{가장 의심되는 모듈이나 데이터 상태}`
* **확인 결과:** `{실제 원인 판명 내용 - 예: Redis 만료 시간 설정 오류, Null 값 검증 누락 등}`
* **핵심 원인:** `{결론 지어진 진짜 원인}`

## 💡 3. 해결 방법 및 조치 (Resolution)
* **수정 코드:** `{수정된 로직의 핵심 아이디어나 스니펫}`
* **조치 내용:** `{코드를 어떻게 바꾸어 문제를 해결했는지 설명}`

## 🛡️ 4. 재발 방지 및 검증 (Prevention & Verification)
* **검증 방법:** 문제를 재현했던 환경에서 정상 작동하는지 확인한 방법
* **방지 대책:** `{예: 테스트 코드 추가, 빌드 파이프라인 검증 단계 추가 등}`

```

## 4. Design Ticket (설계 티켓)

> **목적:** 기능이나 모듈을 본격적으로 만들기 전, 아키텍처적 구조를 정의하고 트레이드오프를 비교하여 방향성을 확정합니다.

```markdown
# [Design] {모듈/컴포넌트/시스템 디자인 주제}

## 🎯 1. 설계 목표 (Goals)
* 이 설계를 통해 해결하고자 하는 구조적 문제
* **지향점:** `{예: 느슨한 결합(Loose Coupling), 단일 책임 원칙(SRP) 준수, 유지보수성 극대화}`

## 🏗️ 2. 시스템 / 모듈 구조
* **의존성 방향:** `{모듈 간의 참조 관계나 레이어드 아키텍처 구조 설명}`
* **핵심 객체/인터페이스 설계:**
  * `Interface/Class A`: `{역할 설명}`
  * `Humble Object B`: `{비즈니스 로직과 프레임워크 의존성 분리 역할}`

## ⚖️ 3. 주요 고려사항 및 트레이드오프 (Trade-offs)
> 특정 방식을 선택하면서 포기한 것과 얻은 것을 비교합니다.

* **선택안 A:** `{예: QueryDSL Projections를 이용한 DTO 직접 조회}`
  * 👍 **장점:** DB 읽기 성능 최적화, 불필요한 엔티티 영속화 생략
  * 👎 **단점:** 영속성 컨텍스트의 변경 감지(Dirty Checking) 기능 활용 불가
* **결론:** `{최종 선택안과 그 이유}`

## 📅 4. 다음 실행 과제 (Action Items)
* [ ] `{도메인 모델링 및 다이어그램 구체화}`
* [ ] `{핵심 인터페이스 및 추상 클래스 스케치}`
* [ ] `{팀 리뷰 또는 AI 피드백 세션 진행}`

```

## 5. Project Ticket (프로젝트 기켓)

> **목적:** 마일스톤 관리용으로, 당초 계획(기획) 대비 현재 어디까지 왔으며 변경되거나 조율이 필요한 간극(Gap)이 무엇인지 싱크를 맞춥니다.

```markdown
# [Project] {프로젝트명/마일스톤명} - 현재 단계 점검

## 🗺️ 1. 프로젝트 현재 상황 개요
* **현재 마일스톤:** `{예: MVP 개발 Phase 1}`
* **진척도:** `{예: 70% 완료, 일부 기능 지연 중}`

## ⚖️ 2. 기존 기획 vs 현재 단계 비교
| 기능/도메인 | 기존 기획 (Plan) | 현재 단계 (Actual) |
| :--- | :--- | :--- |
| **{예: 실시간 알림}** | 카프카(Kafka) 기반 대규모 트래픽 처리 | 현재 Spring 이벤트를 활용한 인메모리 처리 단계 |
| **{예: 이메일 인증}** | Redis를 활용한 인증 코드 캐싱 구현 | 기획대로 구현 완료 및 통합 테스트 중 |

## ⚠️ 3. 기획 상의 차이점 및 변경 사유 (Gaps & Discrepancies)
* **이슈 항목:** `{예: 카프카 도입 일시 보류}`
* **변경 사유:** `{예: 현재 단계에서는 오버엔지니어링으로 판단되어, Phase 2 동시성 및 트래픽 확장 시점에 도입하는 것으로 우선순위 조정}`
* **영향도:** `{예: 인프라 공수 감소로 인해 전체 MVP 출시 일정 1주일 단축 가능}`

## 📋 4. 향후 계획 및 액션 플랜
* [ ] `{지연된 기능에 대한 리소스 재배치}`
* [ ] `{변경된 기획 요건에 맞춘 차기 구현 티켓 발행}`

```
